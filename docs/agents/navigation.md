# Symptom-to-owner map

Start with the affected thread's live metadata, not the repository named in the symptom:

```sh
t3 chat show <thread-id>
t3 project show <project-id>
```

Identify the project root, thread worktree/branch, and provider instance before following a row.
Use the CLI connected to the affected server; see [live-target discovery](../../.agents/references/scars/full.md#provider-tools-and-workspace-ownership) if the target is unclear.

| Symptom                                                | First diagnostic                                                                                                                                                                                       | Code owners                                                                                                                                                                                                                                                                                                  | Reference                                                                             |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Agent sees the wrong project                           | Compare the recorded worktree with `git -C <worktree> rev-parse --show-toplevel --git-common-dir`. If Git ownership is correct, inspect the selected provider's cwd, environment, and extension tools. | [Client bootstrap](../../apps/server/src/orchestration/clientCommandDispatcher.ts), [workspace admission](../../apps/server/src/orchestration/workspaceAdmission.ts), [provider cwd resolution](../../apps/server/src/checkpointing/Utils.ts) (`resolveThreadWorkspaceCwd`)                                  | [Pi workspace diagnostics](../providers/pi.md#workspace-diagnostics)                  |
| Sending a turn takes too long                          | Separate command receipt/commit, checkpoint capture, provider readiness, prompt dispatch, and first model output.                                                                                      | [Command engine](../../apps/server/src/orchestration/Layers/OrchestrationEngine.ts), [provider command reactor](../../apps/server/src/orchestration/Layers/ProviderCommandReactor.ts), [provider service](../../apps/server/src/provider/Layers/ProviderService.ts)                                          | [Turn-start timing](../observability.md#turn-start-timing)                            |
| Worktree cleanup fails or appears stuck                | Distinguish a registered checkout awaiting eligibility/reservation from an already-detached directory in `.t3-worktree-trash`; inspect the item's status, reason, and retry time.                      | [Deletion reactor](../../apps/server/src/orchestration/Layers/ThreadDeletionReactor.ts), [cleanup batch](../../apps/server/src/storage/StorageCleanup.ts), [worktree contributor](../../apps/server/src/storage/contributors/worktrees.ts)                                                                   | [Cleanup entry points](../worktree-cleanup-reconciliation.md#diagnostic-entry-points) |
| Created PR has no thread association                   | Check the creation result and association intent against the thread's current repository/branch. A manual link is distinct from the workspace PR association.                                          | [Creation automation](../../apps/server/src/pullRequestMonitor/PullRequestCreationAutomation.ts), [association recovery](../../apps/server/src/pullRequestMonitor/PullRequestAssociationRecovery.ts), [association validation](../../apps/server/src/pullRequestMonitor/pullRequestAssociationValidation.ts) | [PR delivery](../../.agents/skills/create-pr/SKILL.md)                                |
| Findings go to the reviewer instead of the implementer | Compare the monitor's owner with associated-thread candidates and review-workflow provenance; PR association alone does not establish implementation ownership.                                        | [Owner selection](../../apps/server/src/pullRequestMonitor/PullRequestMonitorService.ts), [review handoff](../../apps/server/src/pullRequestMonitor/PullRequestReviewHandoffReactor.ts), [thread delivery](../../apps/server/src/pullRequestMonitor/threadDelivery.ts)                                       | [Feedback retrieval and provenance](../pr-monitor-feedback.md)                        |

In server subsystems, `Services/` defines contracts and `Layers/` implements them. Follow the
selected provider's `Layers/<Provider>Adapter.ts` only after identifying its instance; a
shared orchestration symptom does not imply a particular provider.

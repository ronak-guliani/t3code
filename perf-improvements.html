#1 — Cap projection bootstrap replay + SQL-side hydration limits

Why first
One retired projector pins global minCursor and replays GBs on every startup; full histories are decoded in JS and can exceed the V8 heap. Cf. scars #129–#131.
Files
apps/server/src/orchestration/Layers/ProjectionPipeline.ts:1686-1709, apps/server/src/persistence/Layers/OrchestrationEventStore.ts:209-264, apps/server/src/orchestration/Layers/ProjectionSnapshotQuery.ts:214,2319
Problem: deleteExcept() + sequential getByProjector loop → min(cursors) → readFromSequence(minCursor, MAX_SAFE_INTEGER). Restart hydration decodes full payload_json before applying the per-thread 200-item cap in memory.
Fix: prune retired cursor rows before computing minCursor; batch-commit + parallel getByProjector; push THREAD_DETAIL_ACTIVITY_WINDOW cap into SQL with keyset (created_at, activity_id) before JSON decode; cap listThreadMessageRowsByThread / getShellSnapshot live tables.
-- before: decode everything, cap in JS
SELECT payload_json FROM projection_thread_activities ORDER BY thread_id, created_at;
-- after: cap per thread in SQL
SELECT * FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY thread_id ORDER BY created_at DESC) rn
FROM projection_thread_activities) WHERE rn <= 200;

#2 — Parallelize snapshot queries, drop read-transaction

Impact
Every WS connect / shell snapshot holds the SQLite write lock while doing 8–10 serial round-trips. Blocks heartbeats.
Files
apps/server/src/orchestration/Layers/ProjectionSnapshotQuery.ts:1458-1520,1800,2162,2286, apps/server/src/ws.ts:1121-1134
Problem: getSnapshot / getShellSnapshot / getThreadDetailById wrap 8–10 list*Rows calls in sql.withTransaction(Effect.all([...])) with no {concurrency} — Effect defaults to sequential.
Fix: add { concurrency: "unbounded" } for read-only fan-out (decode is CPU-bound, SQLite reads are cheap); remove withTransaction for pure reads or use a read snapshot; collapse getThreadDetailById 9 trips → 2–3 joins.
// before
Effect.all([listProjectRows, listThreadRows, listActivityRows, ...])
// after
Effect.all([...], { concurrency: "unbounded" }) // no withTransaction for reads

#3 — De-serialize shell-summary reconciler

Impact
O(threads × (4 queries + full JSON parse + sort)) serialized behind Semaphore(1). Bootstrap drain stalls startup.
Files
apps/server/src/orchestration/projection/ProjectionReconciler.ts:109-145, apps/server/src/orchestration/Layers/ProjectionPipeline.ts:1633-1710, apps/server/src/persistence/Layers/ProjectionThreadActivities.ts:18,116-136
Problem: Effect.forEach(ids, refreshShellSummary, {concurrency:1}); each refresh does 4× listByThreadId (SELECT payload_json … ORDER BY) + per-row Schema.fromJsonString + in-JS filter/sort.
Fix: only refresh summaries for events that change summary fields (scar #127) with concurrent repo reads; maintain incremental summary columns instead of full-history re-derive; see existing good pattern at sidebarState.ts:147 with unbounded concurrency.

#6 — Stop O(n²) markdown re-parse on every token

#8 — Bound checkpoint diffs: fewer git spawns, streamed parse

Impact
Each diff fans out ~6 git processes + holds multiple 10 MB strings; concurrent requests fork-storm + GC churn.
Files
apps/server/src/checkpointing/Layers/CheckpointStore.ts:27-28,365-516,614-682, apps/server/src/checkpointing/Diffs.ts:44-115, apps/server/src/ws.ts:1023-1068
Problem: rev-parse ×2 + reflog --max-count=1000 + for-each-ref --no-contains + rev-list ×2 + diff --numstat + diff patch (10 MB caps each); matchAll(/^diff --git/gm) + per-file slice + toSorted(localeCompare); 5s base-projection cache barely helps. Scars #68, #72–#73 apply.
Fix: resolve refs once and reuse OIDs; share one unified-diff parse (attach raw sections to parsed metadata); stream numstat/patch instead of buffering 10 MB; raise cache TTL with head-aware invalidation; coalesce concurrent identical diffs.

#9 — Bound FTS5 hits before windowing, single MATCH

Impact
Search computes rank for every match, windows it, discards most, then runs MATCH twice.
Files
apps/server/src/orchestration/Layers/ProjectionSnapshotQuery.ts:2548-2596
Problem: hits AS MATERIALIZED (… MATCH … rank AS score) → unbounded ranked (ROW_NUMBER …) → LIMIT 20 → second JOIN … WHERE MATCH + snippet(…,20). Violates scar #15 intent (materialize rank before windowing, snippet only selected rows — second MATCH doubles the work).
Fix: ranked AS MATERIALIZED, ORDER BY bm25(), cap hits … ORDER BY score LIMIT 500 before windowing, keep snippet() only on top_hits.
-- after
hits AS MATERIALIZED (SELECT ... bm25() AS score ... ORDER BY score LIMIT 500),
ranked AS MATERIALIZED (SELECT *, ROW_NUMBER() OVER (...) FROM hits)
SELECT ... snippet(...) FROM top_hits; -- only here

#10 — Lazy cloud runtime + parallel Electron boot + vendor chunks

Impact
Desktop pays cloud + updater + shell-env + serial HTTP-poll cost and ships an unsplit bundle with prod sourcemaps — slow cold start.
Files
apps/server/src/server.ts:301-392, apps/desktop/src/main.ts:127,133,525-570,1466-1543, apps/web/vite.config.ts:66-74,121-125, apps/server/vite.config.ts:9-33, apps/desktop/vite.config.ts:6-43
Problem: CloudRuntimeLayerLive eagerly builds relay/token/awareness (scar #21) even with no cloud link; window waits on 60s waitForHttpReady instead of fd3 listening signal; AUTO_UPDATE 15s + 4h poll races first-second I/O; web/server/desktop Vite configs lack manualChunks and leave sourcemap:true on; patched deps risk missing from dist/bin.mjs (scar #75).
Fix: Layer.unwrap-gate cloud on desired-link config, start awareness after http.wait; spawn backend + create loading window in parallel, navigate on listening; defer updater/shell-env off critical path; add manualChunks {vendor, tanstack, effect}, sourcemap:hidden for prod, bundle patched deps and verify packed artifact.
